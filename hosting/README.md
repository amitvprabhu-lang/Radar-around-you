# Keeping live data fresh on Hostinger Business Web Hosting

Hostinger's support says Business Web Hosting does not support Python, even a plain script run by cron. The collector is Python, so it runs on GitHub's machines. Two small PHP jobs, which cron does support, connect it to your site.

```
your cron (every 10 min) -- trigger.php --> GitHub starts the collector (Actions) --> data branch
your cron (every 10 min) -- pull.php -----> copies the finished files into  <your site>/live/
visitors' browsers read <your site>/live/manifest.json and the files it names
```

Why not rely on GitHub's own schedule: on 2026-10-05 the repository's every-10-minutes schedule ran twice in about five hours. Your server's cron keeps time.

## One-time setup
1. **Secret for the collector.** On GitHub: the repository, Settings, Secrets and variables, Actions, New repository secret. Name `CONTACT_EMAIL`, value a real address (CelesTrak and MET Norway ask callers to identify themselves; it is sent in a header and not published).
2. **A token that can only start the collector.** GitHub, your profile, Settings, Developer settings, Personal access tokens, Fine-grained tokens. Repository access: only `Radar-around-you`. Permission: Actions, Read and write. Nothing else. Choose an expiry and put a reminder in your calendar; when it expires the trigger log will say so.
3. **Upload three files** from this folder (`lib.php`, `pull.php`, `trigger.php`) to a folder that is not inside any website, for example `~/radar-tools/`. Copy `radar-config.example.php` to `~/radar-tools/radar-config.php` there and paste the token in. Never place the config inside `public_html`, and never commit it.
   To keep the token out of the screen, the chat and the shell history, over SSH wait for the server prompt, paste this one line, wait for "Paste the token", then paste the token (nothing shows) and press Enter. It writes the file readable only by you:
   `read -rsp "Paste the token, then press Enter: " T; echo; umask 077; printf "<?php\nreturn [\n    'token'    => '%s',\n    'owner'    => 'amitvprabhu-lang',\n    'repo'     => 'Radar-around-you',\n    'workflow' => 'live-data.yml',\n    'ref'      => 'main',\n];\n" "$T" > ~/radar-tools/radar-config.php; unset T; chmod 600 ~/radar-tools/radar-config.php; php -l ~/radar-tools/radar-config.php`
4. **Two cron jobs** (hPanel, Advanced, Cron Jobs. On the owner's account this page is under a regular site, not under the Node Web App `zeninnov8.com`, which has no such page. Use the Custom mode and the full command; times are UTC, which does not matter for every-10-minutes). Check the PHP version first with `php -v` over SSH or in hPanel; the code needs PHP 7.4 or newer and the `curl` extension or `allow_url_fopen`.
   - `php /home/USER/radar-tools/trigger.php --config=/home/USER/radar-tools/radar-config.php --log=/home/USER/radar-tools/trigger.log`
   - `php /home/USER/radar-tools/pull.php --dest=/home/USER/domains/YOURDOMAIN/public_html/live --pages-dest=/home/USER/domains/YOURDOMAIN/public_html --log=/home/USER/radar-tools/pull.log`
   `--pages-dest` also copies the finished pages (the satellite count page, the satellites by country hub and country pages, and their sitemap) from the data branch's pages/ folder, and then pings IndexNow for the pages that changed (see below; `--no-indexnow` turns that off); leave it out and only the data files are copied. The country pages need the `lib.php` of 2026-10-05 or later on the server; an older copy refuses them and keeps copying the count page. `lib.php` allows exactly five country slugs (united-states, china, united-kingdom, cis-former-ussr, japan); a new country page needs its slug added there and `lib.php` copied to the server again.
   Offset them by a few minutes (for example trigger at :00, :10, ... and pull at :04, :14, ...) so the pull usually finds data the collector has just published.
5. **Check:** after the first run read both logs. `trigger.log` should say "collector started". `pull.log` should say "ok" and `live/manifest.json` should exist on the site. Open the site: the Data tile should change from "Snapshot" to "Live".

## What to expect, and not
- The first collector run builds the satellite catalogue (about 50 requests to CelesTrak). It ran for real on 2026-10-05 and took 4 minutes 13 seconds; later runs restore the catalogue from the `data` branch and took about 1 minute 8 seconds.
- Data reaches visitors about 10 to 25 minutes after the source publishes it: the collector's own schedule, GitHub's 5-minute cache on raw files, your pull, and the app's 5-minute check. Fires and some others are slower at the source.
- If a pull fails halfway, the old manifest stays, so visitors never get a manifest that points at missing files. Old versions are removed one run after they stop being current.
- **Tested on 2026-10-05:** a redeploy of the Web App clears the `live/` folder (a test file was served before and was gone 14 seconds after the push). The next `pull.php` run puts everything back, because it downloads every file the manifest names that is missing; see `docs/hosting.md`.
- **Unknown until tested on your account:** whether a deployment also clears folders outside `public_html` (keep the scripts and the token file there and check after the next deployment), whether cron can run PHP at the interval you set, and how GitHub treats a workflow started every 10 minutes (it should only cost free minutes for a public repository; check GitHub's current billing page).

## IndexNow pings (added 2026-10-06)
After the page copy, `pull.php` tells IndexNow which pages changed, so search engines that take part can fetch them sooner. Design: section 2b of `docs/superpowers/specs/2026-10-06-live-hazard-pages-design.md`.
- **Which engines.** The IndexNow FAQ (read on 2026-10-06) lists Amazon, Bing, Naver, Seznam.cz, Yandex and Yep as participants and says a submission to one endpoint is shared with all of them. Google is not listed; Google finds the pages through the sitemaps named in `robots.txt` and through Search Console, and no Google ping is sent.
- **What is sent.** One POST of JSON (`host`, `key`, `keyLocation`, `urlList`) to `https://api.indexnow.org/indexnow`, with the address of each changed page as its folder (for example `https://<site>/satellites-by-country/japan/`). Only pages that the page copy itself accepts are sent: those it rewrote in that run, plus those still pending from an earlier run (see Throttle and Failures). `sitemap-live.xml` is never sent. The site address and the key come from `pages/index.json`; the site address must be a plain lowercase `https` host with no path or port, or nothing is sent.
- **Proof of the key.** The key is `site/indexnow.key` in the repository. It is public by design, not a secret: the site build writes it as `/<key>.txt` at the site root (only when the site is indexable), and `pull.php` sends nothing unless that file exists on the site and holds exactly the key. See `docs/hosting.md`.
- **Throttle.** Each page is sent at most once every 6 hours (OURS; the FAQ asks sites not to submit the same address many times a day). `indexnow.json` next to the log keeps, for each page, the time of its last accepted send, and a `pending` list of pages that changed but were not accepted yet. A page that changes again inside the 6 hours goes on the pending list and is sent once the 6 hours are up, even if it does not change again. The file holds only allowed page paths, so it stays small; a corrupt or odd file counts as empty (pending pages in it are then lost, and are sent again only when they next change). This needs `--log`; without `--log` nothing is sent and the pull prints why. If the state file or its folder cannot be written, nothing is sent either (`indexnow: state file not writable, nothing sent`), because the throttle could not hold.
- **Failures.** 200 and 202 count as success. Anything else (403 key not accepted, 422 addresses not matching the host, 429 too many requests, no answer) is logged with its status; the pages stay on the pending list with no new send time, and the same run does not retry. A missing or different key file also keeps them pending (no request is made, so it does not count as a failed send). Redirects are not followed for this request, so a redirect answer is a failure too. It never changes the pull's exit code.
- **Retry delay after a failed send** (OURS, so a page the endpoint keeps refusing is not posted every ten minutes; the IndexNow FAQ asks sites not to resubmit without meaningful changes). The rules, all per page:
  1. A page is sent only when both hold: it was not accepted in the last 6 hours, and, if it has a failure record, its retry time has come.
  2. A failed send (any status other than 200 or 202, including 429, a redirect, no answer, or an error) adds one to the page's `failures` and sets `retryAt` to the failure time plus 1 hour after the first failure, 2 after the second, 4, 8, and then 12 hours for every further failure.
  3. A change to the page does not shorten that wait: only a page with no failure record is sent as soon as its 6 hours are up.
  4. A 200 or 202 removes the failure record (and the page leaves the pending list); the next failure starts again at 1 hour.
  5. A record whose `failures` is not a positive whole number, or whose `retryAt` is not a whole number or lies more than 12 hours ahead, counts as no record. Records exist only for pending pages.
- **Log lines** (one per run, in `pull.log`): `indexnow: sent N url(s) (HTTP 200)`, `indexnow: nothing due`, `indexnow: key file missing or different, nothing sent`, `indexnow: the site is noindex, nothing sent`, `indexnow: HTTP 429 too many requests, ...`, `indexnow: turned off (--no-indexnow)`, `indexnow: state file not writable, nothing sent`, and a few others that name the reason.
- **Off switch.** Add `--no-indexnow` to the pull cron command, or delete `site/indexnow.key` from the repository (the next deployment then writes no key file and the next GitHub build writes no key into `pages/index.json`, so the server sends nothing). A noindex site (`SITE_NOINDEX=1`) is never pinged.
- **Owner's step.** Copy `lib.php` and `pull.php` to the server again (the same copy as before). The cron command does not change, as long as it already carries `--pages-dest` and `--log` as shown above.
- NOT CONFIRMED: whether any engine crawls the pages sooner because of the pings; what `api.indexnow.org` actually answers for this site (no request was ever sent from development; the first real answer will be in `pull.log`); whether Hostinger serves `/<key>.txt` (open it in a browser after the next deployment); whether the cron command on the server carries `--log` (if it does not, the pull prints `indexnow: no state file` and sends nothing). After a redeploy the next pull rewrites every live page (the deploy-time copies differ from the GitHub-built ones), so they all count as changed; the 6-hour throttle limits that to one ping per page.
- Known limitations: (1) The site address sent comes from `pages/index.json` on the data branch; the server does not pin it. A damaged or hostile index could name another site, but that site's search engines would refuse the ping because the key file is not on that site, and whoever can change the data branch can already change the pages themselves. (2) Two pull runs that overlap (a run taking longer than the cron interval) can each read the state before the other writes it, so one run's update can be lost; the worst case is one duplicate ping for a page, or a pending page forgotten until it next changes.
