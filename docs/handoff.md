- A push to `main` triggered a new deployment within seconds to a few minutes (observed twice). Hostinger's panel names for buttons were not verified.
- A redeploy wipes extra files inside `public_html` (a probe file in `public_html/live/` was gone after a deployment). `pull.php` restores the live folder on its next run; tests in `hosting/tests/run.php` cover it. NOT CONFIRMED: whether a deployment also clears folders outside `public_html`.
- Content types: `.json` as `application/json`, `.bin` as `application/octet-stream`, `sw.js` as `application/x-javascript` with a seven day cache lifetime, `manifest.webmanifest` as `text/plain`. NOT CONFIRMED: whether installing the app works with that manifest type (test on a real phone).
- The first deployment stalled at the loader because `index.html` was a bare fragment with no charset (read as windows-1252, which broke a regular expression in the script). Fixed by `asDocument` in `site/build.mjs`; `npm run e2e:site` reproduces the failure on the old output.
- Python is not supported on this plan, even from cron (per Hostinger support). So the collector runs on GitHub Actions and two PHP cron jobs connect it to the site; see `hosting/README.md`.

## Known flaky checks
Under heavy load or on a slow renderer, timing-based browser checks have failed without a code change: ISS tap, constellation labels, guide text, Under panel text and the clock speed-up measurement (from the cloud sessions). Each was investigated and made more robust, with no guarantee they never flake. If one fails, rerun alone before debugging, and never run two browser suites at once.

Found on the Mac on 2026-10-05:
- **Slow page start under load.** With a load average of 10 to 25 (another project's build was running), the same page took 78 seconds to start against 10 to 18 seconds on a quiet machine, which beat the 60 second loader waits. The suite crashed at a different step each time. Stopping the other job (`kill -STOP`) and closing browser panes with a 3D page open fixed the timing.
- **Pages left open.** The About-links check opened two pages and never closed them; they kept drawing and starved the next page. Now closed in `e2e.mjs`. This is a likely cause of the repeated startup timeouts, but it was not proven separately from the load.
- **One unexplained `e2e:live` failure.** One run failed 9 checks because the page stayed on the bundled snapshot and fetched none of the test's live feeds, then crashed on a null `fetchedAt`. The rerun on the same code passed 112 of 112. The cause is NOT CONFIRMED (a timing problem is a guess). If it recurs, look at the first live scenario in `e2e-live.mjs` and how the page's first poll is triggered.
